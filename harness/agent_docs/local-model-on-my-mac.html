In an early version of my portfolio, a visitor could ask my AI guide a question and have Qwen generate the reply on my Mac. The site ran on Fly.io. A small worker on the Mac reached out to the site for inference jobs, so Ollama could stay on localhost.

Getting the model running on my Mac

I started with the whole stack on the Mac. The project’s development launcher started Ollama, the FastAPI app, and a local Temporal server and worker. Ollama served qwen3.8:27b over loopback. These were the model settings in the project’s example environment.

MODEL_PROVIDER=ollama
OLLAMA_MODEL=qwen3.8:27b
OLLAMA_BASE_URL=http://127.0.0.1:11434
OLLAMA_CONTEXT=16384

With the tools installed, I started the stack with .venv/bin/python scripts/dev.py and opened the portfolio at localhost:8000. The launcher pointed Ollama at .runtime/models/ and disabled its cloud features. With the server running, I could download the model from the command line.

.runtime/tools/ollama/ollama pull qwen3.8:27b

I used a 16,384-token context window to leave memory headroom and kept retrieved notes short enough to leave room for the conversation and the answer.

How a visitor’s question reached Qwen

On Fly.io, the app saved each question in SQLite before a Temporal workflow ran the agent. The app gave Deep Agents the conversation, my published profile and voice guidance, and relevant excerpts from published notes. The hosted app had an export of the material I’d approved for the site. My private notes and local conversations stayed with the local app.

  1. QueueWhen the agent needed a model response, the hosted app queued an Ollama chat request.
  2. GenerateThe Mac worker claimed the job over authenticated HTTPS and sent it to Ollama on localhost.
  3. ReturnThe worker posted the result back to Fly.io, where the agent picked up the turn.

Qwen could request a tool, such as a search of my published notes. The hosted agent ran the tool and sent its result back to the model in another call. Once the agent had a final answer, the app saved it and the browser displayed it. Temporal tracked completed model and tool calls so a restarted worker could resume from recorded results. An interrupted call could still run again.

What changed once people could use it

The worker ran as a macOS LaunchAgent. It checked that Qwen was installed and sent a heartbeat about every eight seconds. At first, the site chose the Mac for new turns when it had seen a heartbeat in the previous 25 seconds. Otherwise, new turns went to OpenAI. Each turn kept its selected model on retry.

Replies from the Mac could take longer, especially if the agent needed several model calls to finish a turn. I added a macOS idle-sleep assertion during active inference. Closing the lid or putting the Mac to sleep still took it offline. I eventually made OpenAI the default and put Qwen behind an experimental choice. If the Mac is offline, visitors can start a new turn with OpenAI. The model choice is visible before they send.

Keeping both options gave me room to experiment with how Qwen used my notes and voice guidance. The same code saved the question, gathered evidence, and resumed the turn whichever model I chose.
