Personal Agent Harness restart benchmark

By $author · November 21, 2026

What happens when a scheduled AI agent loses its worker while waiting for approval or writing to another service? Across 18 trials, every scheduled turn completed with the recorded decision. A crash after the service committed exposed a duplicate-write risk. The same retry produced one write with deduplication enabled and two writes with it disabled.

Results

Each scenario ran three times. A write attempt is a request to the mock service. An effective write is a new record in that service.

In the post-commit trials, the worker died before returning its receipt to Temporal. Temporal retried the write activity. The deduplicating service returned the first receipt for the same key. The control returned a second receipt and kept both records. In the decline trials, the workflow completed without calling the write tool.

How the restart test works

  1. Trigger a real Temporal Schedule and use the harness’s dispatcher to start one Deep Agents turn. A deterministic model reads a synthetic library notice and prepares a digest for review.
  2. Kill the worker at one of three boundaries. The review is pending, the reviewer approved but the write has yet to start, or the service committed but the receipt has yet to reach Temporal.
  3. Start a replacement worker on the same task queues. Compare the stored decision, the Temporal Activity history, the mock service’s recorded writes, and the final response.

The mock service checks approval against the digest hash before it accepts a write. Its idempotency key combines the scheduled turn ID with that hash. Both remain stable across Activity attempts.

Reproduce the benchmark

Install Git, Python 3.12, uv and the Temporal CLI. The reported run used Python 3.12.16, Temporal CLI 1.9.1 with Server 1.32.0, and Python SDK 1.35.0 on macOS arm64.

git clone https://github.com/emmanueljob/personal-agent-harness.git
cd personal-agent-harness
git checkout $runner_revision
uv sync --locked
.venv/bin/python -m experiments.restart_benchmark --trials 3 --output restart-results.json

The benchmark starts its own loopback Temporal server and uses synthetic data in temporary directories. No model key or app configuration is required. Add --case after_write to run only the idempotent post-commit case, or use --temporal-cli to supply an executable path.

In the JSON output, look at sink_write_attempts, effective_writes, events, and temporal_activities. After a post-commit crash, the idempotent case should show two attempts, one record, and the same receipt twice. The non-idempotent control should show two records and two receipts.

What the results cover

The scheduler, dispatcher, agent workflow, and checkpoint code came from the harness. The model, approval inbox, and downstream service were fixtures. Each interruption killed one worker while Temporal and both databases stayed up. The roughly 11-second recovery reflects the fixture’s 10-second Activity timeout and retry delay.

The measured source revision was 6ebcca32. The checkout in the reproduction steps pins the merged revision with the same benchmark code.
