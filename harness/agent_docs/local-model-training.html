What this project is

An educational supervised fine-tuning experiment. We are learning from the owner’s writing. Each example gives an input and a desired reply; training nudges the adapter toward that reply. This is not reinforcement learning, and no OpenAI teacher responses were used as training targets in these runs.

Why Qwen and MLX

We optimized the first experiment for learning: run it on the Mac we already had, inspect every stage, and make another attempt cheaply. We did not run a benchmark that proved this was the best possible stack.

Four different choices often get mixed together

Qwen is the pretrained model. MLX is the software that executes the numerical operations. QLoRA is the adaptation strategy. Supervised fine-tuning is the learning objective. Changing one does not necessarily require changing the others.

Why MLX on this Mac?

A neural network is largely a program that performs enormous numbers of operations on arrays. MLX provides those operations, automatic differentiation for training, and execution on Apple Silicon. MLX-LM gives us a relatively direct path from a supported model checkpoint to a working local fine-tuning loop.

On Apple Silicon, the CPU and GPU share a physical memory pool. MLX uses that arrangement without requiring explicit transfers between separate CPU and GPU memory allocations. That is convenient for this machine, but it does not turn 48 GB into unlimited model capacity: macOS, other applications, activations, temporary buffers, and the model all compete for resources. Memory bandwidth and computation still matter. MLX’s unified-memory explanation.

Our choice was practical, not exclusive. PyTorch’s MPS backend can also run GPU workloads on a Mac. A PyTorch/CUDA stack on NVIDIA hardware is another route. The differences include supported operations, model implementations, training tools, deployment formats, and performance for the particular workload. We have not measured those alternatives here, so this tutorial makes no claim that MLX would beat them. PyTorch MPS documentation.

Why a 1.7-billion-parameter model?

“1.7B” describes the approximate number of learned parameters, not the number of facts it knows. This model was small enough to download, load, train, and evaluate quickly. A ready-made MLX checkpoint removed a conversion step. That shortened the feedback loop for a first exercise.

The tradeoff is limited starting capability. A small model can be more brittle about instructions, writing quality, and unusual inputs. An adapter changes the behavior of that starting model; it does not automatically grant the reasoning or world knowledge of a much larger one. We have not established that 1.7B is the right size for a useful personal assistant.

Nor was 4-bit the only plausible choice on a 48 GB Mac. A higher-precision base with LoRA is a reasonable comparison to run. We selected the compact path for inexpensive iteration, and now we have a concrete result to diagnose. The exact base revision we downloaded.

Why the target matters more than the transcript volume

A transcript contains several voices, tool output, instructions, and repeated context. If we train indiscriminately on everything, the model can learn to imitate the collaborator or reproduce operational clutter. We used the owner’s messages as targets, with other material serving only as context when useful.

For the drafting task, the dataset’s final assistant slot contains the message we want the model to produce: the owner’s words. That is a training-interface role, not a claim that the original author was the assistant. The original writing remains attributed to the owner.

The first pass asked the model to predict the next owner message from context. That mixes two challenges: deciding what the person would want next and choosing how they would say it. There can be many reasonable next thoughts. The curated pass supplies a tutor-written intent brief and teaches the original phrasing. It is a narrower rewriting task, and the brief is annotated from the target; it does not test independent discovery of personal intent.

What does one example teach?

The tokenizer converts the input and target text into token IDs. During training, the model sees each correct preceding target token and predicts the next one. This is often called teacher forcing. “Teacher” here refers to supplying the correct sequence, not to using another AI model to generate the training data.

Prompt masking means the instructions and intent are visible but their tokens do not contribute to the scored target loss. We also include the end-of-message token as a target. Learning when to stop matters for a drafting model. Our generation still sometimes hit its 160-token cap, which is an observed failure rather than a successful stopping decision.

Compression and precision

Our model is compressed by quantization: we preserve the architecture and approximate many of its learned numbers using a smaller representation. We did not remove three quarters of the layers, summarize the model into text, or train it from scratch.

First, what is a weight?

A model converts tokens into numerical vectors and repeatedly transforms those vectors. Many transformations multiply them by large tables of learned numbers: weight matrices. Attention uses these transformations to combine information from the context; other layers transform the resulting features. Eventually the model produces scores for possible next tokens.

Weights influence those calculations. A particular weight is not a sentence such as “Emmanuel likes concise answers.” Useful behavior is distributed across many interacting parameters. Learning changes those numbers so that particular outputs become more likely in particular contexts.

What gets smaller?

A 16-bit representation uses two bytes per number. A 4-bit code uses half a byte. If every weight could be stored with exactly four bits, the payload would take one quarter of the storage of a 16-bit version. Actual files also contain scales, offsets, some higher-precision tensors, and metadata.

This is lossy numerical compression. Nearby original values may map to the same stored code. Once that happens, the exact original values cannot generally be recovered from the compressed copy. That differs from a ZIP file, which can reconstruct its original bytes exactly.

INSPECTED IN OUR CHECKPOINT

4 bits per quantized weight · groups of 128 weights · BF16 scales and offsets · packed unsigned 32-bit storage · base file: 914,316,100 bytes (914.3 MB).

How can four bits describe a decimal number?

Four bits can identify 16 codes, numbered 0 through 15. A group of weights shares a scale and an offset. To interpret one stored code, the computation reconstructs an approximate weight:

approximate weight = scale × code + offset

Different groups have different scales and offsets. There are therefore many more than 16 possible reconstructed values across the whole model. In our downloaded checkpoint, the quantized layers use groups of 128 weights. Eight 4-bit codes fit into one 32-bit storage word; a tensor labeled U32 in the file is packing several codes together, not giving every original weight 32 bits.

Those details come from the saved configuration, tensor headers, and installed MLX implementation. The public MLX quantization reference describes the grouped affine representation.

Why groups, and why not the smallest possible groups?

If one scale covered a huge matrix, a few unusually large weights could force a very wide range and leave poor resolution for the many small weights. Smaller groups let the scale fit local values more closely, but each group needs its own metadata. There is a storage-and-precision tradeoff; the best grouping is not established by the toy illustration.

Our file uses two BF16 metadata values per group. Each has 16 bits, so the arithmetic is 4 + (16 + 16) / 128 = 4.25 bits per quantized weight, before other tensors and file overhead. This is why “4-bit” does not mean a file that is exactly one quarter the size of every 16-bit version.

Does everything now calculate in four bits?

No. Four bits describes the stored codes for quantized weights. MLX’s quantized matrix multiplication takes packed weights and their scales/offsets, then computes their contribution to floating-point activations. The implementation can interpret packed weights within optimized operations; it need not expand the entire model into a persistent full-size 16-bit copy first. Other tensors and arithmetic have their own precision. Quantized matrix multiplication.

What is the impact on quality and speed?

The smaller representation reduces weight storage and can reduce the amount of weight data that must move through memory. That can help performance on a suitable workload. Unpacking, reconstruction, kernel efficiency, prompt length, batch size, and hardware also matter, so a smaller file is not a guarantee of faster responses.

Rounding changes intermediate calculations and can change next-token scores. Sometimes the output barely changes; sometimes a close token choice flips and later text diverges. The impact varies by model, quantizer, precision, and task. We have not measured a “percentage of intelligence lost,” and such a single number would not describe our use case well.

Most importantly, we cannot blame our repetitive outputs on 4-bit quantization. Both our before and after models use the same quantized base. We changed the adapter and observed a difference. To isolate quantization, we would need matched higher-precision runs with the same data, prompts, generation settings, and evaluation.

LoRA and QLoRA

Fine-tuning does not have to rewrite every weight. We can hold the original model still and learn a compact extra transformation alongside selected layers.

Start with full fine-tuning

In full fine-tuning, the training process can update all the base model’s trainable weights. That gives it many degrees of freedom. It also means storing gradients and optimizer state for a large number of parameters, in addition to weights and intermediate activations. This can require far more memory than loading the same model just to generate text.

More freedom is not automatically useful. With a tiny or unrepresentative dataset, training can push a capable model toward narrow habits or degrade behavior we wanted to preserve. We need evidence that broader updates help the task, not just enough memory to run them.

LoRA: a big adjustment built from two small matrices

A dense layer transforms an input vector x using a weight matrix W. LoRA freezes W and learns two smaller matrices, A and B. Their product provides an update. The shared small dimension is called the rank.

output = W × x + scale × B × (A × x)

Think of a general-purpose transformation with a compact learned correction attached to it. The correction is not a separate chatbot and is not a list of rules. Rank limits the mathematical form of that correction; rank 8 does not mean eight memories, eight personality traits, or eight examples. This is the central construction of LoRA.

OUR ACTUAL ADAPTER

2,490,368 parameters across selected linear projections in the last eight transformer blocks. Rank 8, MLX scale 16, dropout 0. The saved tensors are FP32. The adapter file is 9,973,395 bytes, about 9.97 MB.

Why QLoRA instead of ordinary LoRA?

Ordinary LoRA can use a higher-precision frozen base. Quantized LoRA keeps the same adapter idea but stores the frozen base more compactly. We used the already-quantized Qwen checkpoint, so MLX-LM follows its quantized LoRA path. That keeps the base small while retaining trainable floating-point adapters.

Our practical benefits were cheap local iteration, a small artifact we can inspect, and straightforward rollback: remove the adapter to return to this base model’s behavior. The tradeoffs include the base’s quantization error, the restricted form of the update, and dependence on compatible runtime support. Our measurements do not prove QLoRA gives better writing than ordinary LoRA.

There is a naming nuance. The original QLoRA paper combines a frozen 4-bit base with low-rank adapters and also introduces NF4, double quantization, and paged optimizers. Our run uses MLX’s grouped affine weights and Adam. It follows the central quantized-adapter idea, not every implementation detail of that paper. MLX-LM’s terminology and training guide.

What happens during a training step?

The frozen base and adapter both contribute to the prediction. The loss measures how well that prediction matches the target tokens. Automatic differentiation follows the relevant computation to determine how the adapter parameters affected the loss. The optimizer changes those parameters; it does not rewrite the packed base weights.

“Only 0.145% of parameters are trainable” therefore does not mean only 0.145% of the original computation or memory is required. The whole model still performs the forward pass. Training still needs intermediate activations and the computation needed for adapter gradients. We save most directly on the number of trainable weights, their gradients, and their optimizer states.

What do rank, layers, scale, and learning rate change?

Rank controls the size of each low-rank update. Adapted layers control where updates can enter the model. Increasing either generally increases the trainable parameter count. Scale controls the adapter contribution; in our MLX configuration, 16 is the direct scale setting, not automatically the same convention as another library’s “alpha.” Learning rate controls the optimizer’s update size.

We started with rank 8, eight blocks, scale 16, and learning rate 0.0001 as a small, workable configuration. We did not tune them in a controlled search. Raising rank or the learning rate would not repair contradictory examples or a poorly defined task. Our first diagnostic changes should address the task, data, and evaluation before adding capacity.

What exactly do we save?

The adapter contains the learned matrices and a configuration telling the runtime where to attach them. It requires a compatible base model; it is not a self-contained 10 MB replacement for Qwen and not a portable personality that can be attached to any model. Preserve the base revision, tokenizer/chat template, quantization settings, and adapter configuration together.

Some workflows merge adapter updates into base weights for deployment. Quantized workflows can require dequantization and requantization during that process, which can add rounding differences. We kept a separate adapter, and any future exported or merged model needs its own output checks.

More steps weren’t better.

What “loss” measures

How surprising the real reply’s next tokens were to the model. Lower loss means it predicted those words better. It does not directly measure personality, usefulness, truth, or whether you would send the draft.

Why keep step 19?

We selected the lowest validation loss among evaluated checkpoints, without using test results to choose. Both runs selected step 19. Continuing to step 80 fitted the training data more but did not improve the validation result.

Why can lower loss still produce bad text?

For a target token, the loss is the negative logarithm of the probability the model assigned to that token. Giving the correct token more probability lowers the loss. We average this kind of error across scored target tokens. Perplexity is the exponential of that average loss; it is not a percentage of correct answers.

Training and loss evaluation supply the correct prefix. Free generation feeds the model its own previous choices. A model can improve at predicting reference words while still falling into loops after its own imperfect output. That mismatch is one reason we must read generated text as well as track the curve.

Steps, epochs, and why these runs were short

One optimizer step updates the adapter after processing a batch. Our batch size was one example, with no gradient accumulation, and we ran 80 steps. An epoch means one traversal of the training examples. At this scale, 80 examples’ worth of updates is roughly 1.9 passes over 43 rows or 3.8 over 21 rows; these are rough exposure counts, not evidence of broad learning.

The first training-and-selection call took about 17.6 seconds, and the curated one about 7.9 seconds. Those timings exclude collection, curation, environment setup, downloading the base, and separate output evaluation. They are not estimates for a bigger dataset, longer contexts, or another machine. The runs were small because the learning exercise was small.

Why validation, and why step 19?

Training loss asks how well we fit examples used for updates. Validation asks how the current weights predict separate examples and can guide checkpoint selection. Test examples are then used for a final report. Repeatedly selecting configurations based on test results would blur that separation.

Our callback saved the exact weights associated with each validation measurement. The training library evaluates before the next displayed update, so the first trained evaluation corresponds to 19 completed updates, not 20. Both runs selected that checkpoint. The best point among these few measurements is not proof that step 19 is globally optimal; we did not evaluate every possible schedule or seed.

Read the results

The first pass picked up some habits and repeated them too often. The curated pass improved prediction on its small held-out set, while several base-model drafts still expressed the intention more clearly.

Why are there two generation settings?

Greedy decoding always chooses the highest-scoring next token. It exposed repeated phrases. We then tested the model author’s suggested non-thinking sampling settings on both models: temperature 0.7, top-p 0.8, top-k 20, with a presence penalty of 1.5 and a fixed seed of 42. The MLX presence-penalty window is 20 tokens. This changed generation, not training.

Both modes are capped at 160 generated tokens. Some repetitive outputs reach that cap. The cap is not a natural end-of-message judgment.

What we can conclude—and what remains a hypothesis

The adapter changed the model’s output, and reference-token prediction improved on these small held-out sets. The generated writing still contains repetition, awkward phrasing, and, in the first pass, unsupported details. Several supplied-intent examples are expressed more cleanly by the base model. This is evidence that our current adapter is not ready to replace a dependable writing assistant.

Possible contributors include too little representative data, an ambiguous first task, a small base model, aggressive updates for the dataset, and generation settings. Those are hypotheses, not a diagnosed root cause. Quantization affects both before and after. We would need controlled comparisons to separate its contribution from the others.

The curation pass is also not a clean experiment on “curation alone”: it changed the task framing and the evaluation conversations. Compare each base/adapter pair within a pass. Avoid reading lower absolute loss in the second pass as a direct percentage improvement over the first model.

Voice and knowledge

We extracted source-backed notes from the same conversations. These are records we can inspect and correct. They are not proof that the trained model can reliably recall the facts.

What weights can learn

Patterns in phrasing, preferred formats, and habits of response. Facts can be learned too, but these experiments did not establish dependable personal-fact recall.

What stays in the source store

Dated statements, supporting excerpts, and correctable preferences. Supplying relevant records at answer time lets us check the evidence instead of trusting a familiar-sounding sentence.

Why a familiar tone can create false confidence

A model that says “how would we…” or uses your punctuation may feel more personal. That surface resemblance does not show that it knows the facts behind the conversation. It can also express an invented fact in a familiar voice. We should judge style, intent preservation, and factual grounding separately.

For this project, my design recommendation is to keep factual records and their sources in a correctable store, then supply relevant evidence when needed. That is a system-design inference from our requirements and failures, not a result that this small training run proved. Retrieval makes evidence available; it still needs good selection, relevance, and freshness checks. The RAG paper explains the broader combination of learned models and retrieved information.

A first-pass recall probe failed to recover a stated preference reliably. The curated pass evaluated expression from supplied intent. Dependable personal recall and retrieval would need their own tests.

Beyond the toy

“Toy” describes the scope of the experiment and the strength of its evaluation. We really changed model weights. We have not demonstrated a dependable voice model, personal memory, or retrieval controller.

First decide which product we are trying to build

A voice drafter receives a supplied intention and expresses it in your style. A knowledge assistant answers questions using current evidence. A retrieval controller decides whether to search, what to fetch, and how much context to supply. Those are different jobs, with different training examples and success criteria.

The curated pass focuses on the first job. It cannot establish success on the other two. For a serious version, I would define each behavior separately and keep a simple baseline for each. A trained voice adapter would earn its place only if it improves the writing compared with prompting alone.

OUR LEARNING VERSION

A DEPENDABLE VERSION

More data, but first better coverage

We trained on 43 examples in the first pass and 21 in the curated pass. That is enough to exercise the pipeline and observe a change; it is not enough to represent a person across topics, audiences, moods, and stages of work. A pile of debugging requests can teach the model to sound irritated because that is what the sample rewards.

A stronger collection would include exploration, decisions, disagreement, thanks, corrections, requests for depth, and requests for brevity. It would keep the intention and context together with the final owner-authored message. We would track where an example came from and distinguish actual writing, tutor-written briefs, and any synthetic targets.

There is no defensible magic minimum like “exactly 1,000 emails makes a voice model.” The needed volume depends on task breadth, consistency, the starting model, and observed errors. We would add coverage where evaluation exposes gaps, rather than treating raw row count as progress.

A production test set must survive our curiosity

Once we read a test result and make design choices because of it, that result is part of our development feedback. It remains useful history, but it cannot keep serving as an untouched final exam forever. Before making a reliability claim, we would reserve fresh conversations and scenarios, control near-duplicates, and decide success criteria in advance.

Human evaluation would ask separate questions: Did the draft preserve the intended meaning? Does it sound like you? Is it concise enough for the situation? Did it invent a fact or commitment? Does it repeat? We would also measure latency and memory in the actual serving configuration. Loss and perplexity are useful diagnostic measurements, not substitutes for those judgments.

A fair comparison changes one major factor at a time

Our second pass changed both the selected writing and the task framing. That was a sensible learning move, but it means the difference cannot be attributed to curation alone. A controlled follow-up would keep a shared evaluation set and generation configuration, then vary one major factor.

What would change operationally?

We would version the dataset, training configuration, base revision, and adapter together; retain an evaluation report; and test the exact artifact used for serving. If deployment uses a different quantizer or an adapter merge, the converted model must pass the checks too.

We would measure real prompts and response lengths, cold starts, concurrent requests, and memory use. A local personal tool may still use MLX. A multi-user service may justify a different inference stack or hardware. Those choices should follow measured workload requirements, not the assumption that production automatically means a cloud GPU or full fine-tuning.

Initial use would be draft-only or shadow evaluation: compare what the model would have done while a person keeps control of actual actions. We would retain the previous model and a baseline fallback, monitor regressions, and separate changing factual records from updates to a writing adapter. Personal training material also needs a deliberate retention and access policy; a learned adapter can carry traces of its training data.

What about your original “when should it reach into the brain?” problem?

A useful next experiment could train a small routing model on decisions such as “no lookup,” “retrieve these preferences,” or “search the project history,” with an explicit context budget. The labels would need to describe what information the task actually required. A message written in your style is not a label for the right retrieval action.

We would measure missed necessary retrieval, irrelevant retrieval, whether the useful source was actually found, downstream answer quality, and the time/token cost. Start by comparing against simple rules and the existing agent’s tool selection. A tiny controller earns its complexity if it improves that tradeoff. Moving every personal fact into tiny-model weights would make provenance, correction, and freshness harder to inspect; it would not automatically solve routing.

A serious version can still use the same method.

The biggest upgrade may be a better-defined task, representative examples, careful evaluation, and disciplined operation. MLX and QLoRA are not inherently “toy” tools. Our tiny dataset and limited evidence are what keep this particular result an experiment.

Where reinforcement learning would fit

These runs used supervised fine-tuning on example replies. Distillation can use a teacher model’s outputs as training targets. Reinforcement learning optimizes a reward signal.

What would your feedback train?

A correction paired with its intent can become another supervised example. A preference between two outputs can remain an evaluation judgment or become preference-training data after we have enough reliable comparisons. DPO is one approach that learns from preferred and rejected replies without the separate reward-model and online RL loop often associated with RLHF. It is another possible experiment, not something this website runs. DPO paper.

For our next pass, preserving the intended meaning and your actual correction is the clearest teaching signal. More sophisticated optimization cannot rescue labels that reward repetition or drift away from what you wanted to say.
